# Server-Side Search, Filter & Pagination

Spec for [FUTURE_IDEAS.md](FUTURE_IDEAS.md) item 6: moving `GET /recipes` from "return every row" to a paginated, filterable, sortable endpoint, with the frontend list page driven from that endpoint instead of an in-memory scan over a fully-loaded array.

**Supersedes** `RECIPE_LIST_QUICK_WINS_SPEC.md` Parts 1–2 (client-side search/tag-filter and sort): once the recipe count is large enough, filtering/sorting an array already sitting in the browser stops being the bottleneck and the "fetch everything" call itself becomes the problem, so this moves that logic to the database. Unaffected: Quick Wins Part 3 (total time display) and Part 4 (clone); Part 5 (empty/error state) needs one adjustment, noted below.

**Explicitly out of scope:** infinite/virtual scroll (a Prev/Next + page-number pager is enough for a first cut), configurable page size in the UI (fixed default), full-text search ranking (substring `LIKE` is enough at this scale), any change to the write endpoints.

**Sequencing:** Parts 1→2→3 are a genuine dependency chain (response-shape change → typed client → consuming component), not just file overlap — Part 2 can't start until Part 1's shape exists, Part 3 can't be written against a client that doesn't exist yet.

## Key decisions

- Response envelope (`content`, `page`, `size`, `totalElements`, `totalPages`) replaces the bare array on `GET /recipes` — a breaking change, but with exactly one consumer (this repo's own frontend) it's coordinated in one PR rather than versioned.
- Tag filtering (`hasAnyTag`) uses a **correlated `EXISTS` subquery** against the `recipe_tags` join table (tags are an `@ElementCollection`, not a column), not a `Root.join("tags")` — a direct join against an `@ElementCollection` combined with `Pageable` is a known JPA pitfall: the join multiplies rows per matching tag, and `DISTINCT` alongside `Pageable`/`ORDER BY` on a to-many join is exactly where Hibernate's in-memory-pagination warnings come from. `EXISTS` filters without widening the row set, so DB-level `LIMIT`/`OFFSET` stays correct. Tags are still lazy-loaded per result row when serialized — fine at `size <= 100`; `@BatchSize`/`default_batch_fetch_size` is a later fix if N+1 shows up, not needed now.
- Hand-rolled `RecipePageResponse` DTO rather than serializing Spring Data's `Page<T>` directly, keeping the response contract fully described by `openapi.yaml` per this repo's entity/DTO-separation convention.
- `size` above 100 clamps rather than errors; unknown `sort` field returns 400 (existing `ProblemDetail` shape) rather than being silently ignored.
- Search input debounces 300ms — it's a network call now, not an in-memory scan (Quick Wins explicitly skipped debounce for the old array-scan version; that reasoning no longer holds). Tag/sort/page changes still trigger an immediate refetch (discrete clicks, not a keystroke stream). Changing any filter or sort resets to page 0.
- `q`/`tags`/`sort`/`page` reflect into the route's query params so a reload/shared link reproduces the view — deliberately distinct from Quick Wins' `sortKey`/`sortDir`/`viewMode`, which stay `localStorage`-persisted standing preferences. `q`/`tags`/`page` are per-visit/session state, not a returning-user default (nobody wants three-day-old search text silently re-applied). The URL seeds the initial request; `localStorage` still seeds `viewMode`/initial sort, overridden by the URL if present.
- `availableTags` can no longer be derived from "every loaded recipe" (the frontend never holds the full set), so it's kept sticky: accumulates the union of tags seen across responses fetched so far this session, as a plain merged `signal` rather than a `computed()` over `recipes()` (a computed would silently lose tags once earlier pages scroll out of the current window). Rough edge — brand-new tags on unfetched recipes won't appear as a filter chip until surfaced — accepted for a first cut (worth a code comment, not a dedicated `/recipes/tags` endpoint).
- Quick Wins Part 5's "no recipes at all" vs. "no recipes match" distinction can no longer compare a full in-memory array's length before/after filtering. Reframed on whether a filter is currently active: empty `q`/`tags` + empty page → "no recipes yet" CTA; non-empty filter + empty page → "no recipes match your search" + "Clear filters." Strictly simpler than before and behaviorally identical.

## Shape of the change

- **Backend:** `GET /recipes` gains five optional params — `q` (case-insensitive substring match on title OR description), `tags` (comma-separated, OR among themselves, AND-ed with `q`), `sort` (`field,dir`, default `title,asc`; allowed fields: title/prepTimeMinutes/cookTimeMinutes/createdAt/updatedAt), `page` (default 0), `size` (default 20). `RecipeRepository` gains `JpaSpecificationExecutor<Recipe>`; new `RecipeSpecifications` helper composes `titleOrDescriptionContains()` and `hasAnyTag()` via `Specification.allOf(...)`, each added only when its input is non-blank. `RecipeService.findAll` takes the new params and maps `Page<Recipe>` to `RecipePageResponse`. Nulls-last sort ordering for prepTime/cookTime (a Quick Wins rule) moves from the client comparator to the database. Empty `q`/`tags` behave as "no filter." This is the first real backend test coverage beyond the context-load smoke test: `RecipeRepositoryTest` (`@DataJpaTest`, exercises `RecipeSpecifications` against real H2) plus `RecipeControllerTest`/`RecipeServiceTest`.
- **Contract:** `openapi.yaml`'s `GET /recipes` gains the five parameters (`tags` as `style: form, explode: false`) and a 400 response; new `RecipePageResponse` schema replaces the bare-array 200 response. Edit `openapi.yaml` first, then `npm run api:generate` per `CLAUDE.md`'s cross-repo contract rule; `recipe.model.ts` re-exports `RecipePageResponse` alongside the existing re-exports.
- **Frontend:** the list page keeps Quick Wins' existing toolbar; only what happens after a change fires differs — a debounced `GET /recipes` request instead of a local `computed()`. `RecipeService.getAll()` takes a params object and returns `RecipePageResponse`; `recipeCount` now reads `totalElements`. `RecipeListComponent` drops the now-dead `filteredRecipes`/`sortedRecipes` computeds and comparator functions; adds `page`/`pageInfo` signals (`initialPage()` seeded from `ActivatedRoute` query params, mirroring the `initialViewMode()` pattern), a debounced search stream (`toObservable` + `debounceTime(300)` + `distinctUntilChanged` + `takeUntilDestroyed`), and query-param sync via `router.navigate([], { queryParamsHandling: 'merge', replaceUrl: true })` so the URL stays in sync without a history entry per keystroke. A pager ("Prev"/"Next" + "Page X of Y") appears below the list, disabled appropriately at the first/last page.

## Testing

Backend: `RecipeSpecifications`/repository-level coverage of `q` matching (title/description/neither, case-insensitivity), `tags` OR-matching without duplicate rows, `q` AND `tags` combined, empty-filter behavior; pagination bounds (`totalElements`/`totalPages` correctness, past-last-page returns empty content not an error, `size` clamping); sorting per field and direction including DB-level nulls-last, and the unknown-field 400. Frontend: `RecipeService.getAll()` param passthrough and `recipeCount` source; debounce timing (fake timers) vs. immediate refetch for tag/sort/page; page-button disabling and page-reset-on-filter-change; both empty-state branches and `clearFilters()`; query-param sync in both directions (write on change, seed from params on load).

## Deferred

A dedicated "distinct tags across all recipes" endpoint (fixes the unseen-tags-as-chips rough edge); configurable page size in the UI; revisiting `@BatchSize`/`default_batch_fetch_size` if tag N+1 queries show up in real usage.
